## 快速开始

图形界面（最省事）：

```
双击 启动抢课助手.bat
```

打开后做三件事：填账号密码 → 填「课程代码」或「教师名称」→ 点「▶ 开始抢课」。
第一次用建议先点「**查看可选课程**」，确认能读到课程再开抢。

> 首次启动会自动把 selenium 装进项目内的 `libs\` 目录，**不污染系统环境**，也**不需要**你手动 `pip install`。

命令行四步（详见 [`HOW_TO_USE.md`](HOW_TO_USE.md)）：

```bash
# 1. 装好 Python 3 即可，不用装任何依赖

# 2. 复制配置模板，填入学号 / 密码 / 课程 jxb_id
copy config.example.json config.json

# 3. 不知道 jxb_id 就先列一下
python grab.py --config config.json --list

# 4. 开抢（高峰期建议加 --at，提前跑起来等开闸）
python grab.py --config config.json
```

## 高峰期模式（重要）

抢课开放的那几分钟，服务器会被几千人同时打：响应从 1 秒变十几秒、
大量 502/504、会话被踢、名额几秒就没了。**晚上人少时跑得通，不等于高峰期能用。**

界面上默认勾着「**高速直投提交接口**」，它和普通方式的区别是：

| | 读页面 | 提交 | 30 秒能投几次 |
|---|---|---|---|
| 浏览器点击 | 每次都要 | 点按钮 + 等弹窗 | 个位数 |
| **高速直投** | **只读一次** | 直接 POST 提交接口 | **几十次** |

原理：先读一次选课页把目标课的 `jxb_id` 拿到手，之后**不再读页面**，
直接对着提交接口高频投。正方的提交接口本身很轻（一个 POST 就完事），
而选课列表页服务器要生成一两秒 —— 高峰期的胜负就在这几秒。

**高峰期正确用法：提前 5~10 分钟打开、登录、填好课、点开始。**
开放前显示「待命、提交 0 次」是正常的，它在等正确时机。
中途掉线会用账号密码自动重登（正方不需要验证码）。

### 抗压设计要点

| 设计 | 解决什么问题 |
|---|---|
| **读一次、投多次** | 列表页 1~2 秒，提交只要几十毫秒，把时间全花在提交上 |
| **区分"确定没送到"和"结果不明"** | HTTP 5xx = 请求没到应用，立刻重投；超时/断连才算结果不明，才回查已选列表 |
| **提交接口绝不自动重试** | 超时后服务器可能已经处理了，重发会收到"已满"，把胜利误判成失败 |
| **"已满"也回查一次** | 那个名额很可能就是你自己占掉的 |
| **"已经选过"当成成功** | 那通常是你上一次超时的提交其实成了 |
| **待命期间探活** | 不探活的话会话会在等待期悄悄过期，开放前几秒才发现，续期正好把名额让出去 |
| **"未开放"不触发退避或停止** | 一退避就正好错过开闸瞬间 |
| **SessionLost 与普通网络错误分开** | 高峰期 502 只是"这一下没成"，当成会话失效去重登会一直在登录页打转 |
| **已知地址优先** | 单个入口失败不拖垮整轮扫描，不每次重扫候选列表 |

## 重要修复（本次）

### 1. 提交地址前缀重复 —— 所有选课提交都打在 404 上

`base_url` 是 `http://jwxt.cumtxh.cn/jwglxt`（已含 `/jwglxt`），
但 `submit_select` / `diagnose_select_endpoints` / `_select_referer`
又拼了一次 `/jwglxt`，实际请求变成：

```
http://jwxt.cumtxh.cn/jwglxt/jwglxt/xsxk/xsxk_operate.html
```

结果 **12 种候选端点组合全部落到"页面不存在"**，`submit_select` 只会抛
"没能找到可用的选课端点"。**这就是"真实提交从未验证"的根因。**
现已修复，并在 `test_sim.py url` 与 `test_peak.py` 里加了回归测试。

### 2. `kch_id` 解析不出来

`parse_courses` 只会从 `kch_id=xxx` 这种形式提取，而正方真实页面用的是
`xsxk('jxb_id','X','kch_id','Y')` 这种 JS 调用形式 —— 课程代码一直是空。现已兼容。

### 3. 故障种类没有分清

原来 `FATAL_MARKS` 把三件完全不同的事混在一起：`"不在选课时间内"`（还没开放，
**该继续投**）、`"登录超时"`（会话掉了，**该自动重登**）、`"无选课权限"`
（真的没戏，才该停）。混在一起会导致没开放时直接停掉（正好错过开闸瞬间），
或者会话掉了却不重登。现在 `zf_peak.classify_submit` 把它们分成
`ok / already / full / not_open / session / gateway / stop / unknown` 八类分别处理。

### 4. 高峰期探测一遇抖动就白扫一圈

`find_select_page` 每次都从候选列表第一个开始试，一次网络抖动就要重扫全部候选。
压测里这一条让 brutal 档的定位耗时到了 60 秒级。现在 `find_page` 优先复用
**已经确认过的地址**（快路径），brutal 档定位时间降到 2~4 秒。

## 高峰期压测（`test_sim.py`）

`sim_server.py` 会起一个本地"教务站"，可以注入：慢响应、随机 5xx、连接被掐断、
请求卡死、会话过期、名额被抢、**响应丢失**（服务器其实选上了但回程丢包）。

它**自己生成一对 RSA 密钥，用私钥真的解密**客户端传来的密文再比对明文 ——
所以客户端的裸 RSA（无 PKCS#1 填充、定长大端输出）只要有一点不对就会被识破，
而不是两边共用同一个错误实现。

最近一次全量运行结果（7 个场景，全部 0 失败）：

| 场景 | 结果 |
|---|---|
| **三档强度** normal | 定位 0.2 秒，0.3 秒抢到 |
| **三档强度** peak（25% 请求失败） | 定位 1.1 秒，开放瞬间抢到（提交 8 次，7 次被回"未开放"） |
| **三档强度** brutal（51% 请求失败） | 定位 2.0 秒，扛住 15 次 502 + 4 次断连后抢到 |
| 地址拼接 | 6 个地址全部无重复前缀 |
| 会话中途过期 | 自动重登 1 次，56 秒后抢到 |
| 响应丢失 | 0.8 秒靠「已经选过」回执确认成功 |
| 全站 5xx | 没崩，恢复后 0.9 秒抢到 |
| 密码错误 | 明确提示「用户名或密码不正确」，密文本身合法 |
| 未开放 | 知道开放时间→待命 0 次提交；不知道→8 秒投 23 次，节奏不退让 |

**关于胜率的实话**：peak / brutal 两档里服务器分别有 25% / 51% 的请求在失败，
对手又在开放后 2~4 秒就来抢 —— 比现实恶劣得多，单次存在小概率抢不到。
所以测试对这两档允许重试，normal 档是确定性必须成功。

## 原理

### 登录机制（已对真实服务器验证）

密码是 **RSA 加密**后提交的（不是老版正方的 DES）：

| 步骤 | 请求 | 说明 |
| --- | --- | --- |
| 1 | `GET /jwglxt/xtgl/login_slogin.html` | 建立会话 Cookie，从页面取出 `csrftoken` |
| 2 | `GET /jwglxt/xtgl/login_getPublicKey.html` | 拿到 RSA `modulus` / `exponent`（base64） |
| 3 | 本地计算 | `cipher = pow(密码的整数形式, e, n)`，再 base64 |
| 4 | `POST /jwglxt/xtgl/login_slogin.html` | 表单 `yhm` / `mm`(密文) / `csrftoken` / `language` |
| 5 | 判定 | 成功会跳转；失败页面回显 `用户名或密码不正确` |

> 关键细节：正方前端 `rsa.js` 的 `RSAKey.encrypt` **不做 PKCS#1 填充**，服务端按"裸 RSA"解密。
> 所以必须用裸 `pow(m, e, n)`，**不能**加 PKCS#1 填充，否则服务端解不出来。

实测：`modulus` 为 1024 位，密文固定 128 字节（base64 后 172 字符），
且**每次请求公钥都不同**（动态签发）。本校**没有登录验证码**，
所以掉线后可以全自动重登。

### 选课入口与提交

```
选课 -> 自主选课
  gnmkdm = N253512
  url    = /xsxk/zzxkyzb_cxZzxkYzbIndex.html
```

**选课页在非选课期也会正常打开**，只是提示「对不起，当前不属于选课阶段」并且没有课程数据。
程序能识别这个提示，并明确告诉你"现在不在选课开放时间"。

提交走 `xsxk_operate.html`；脚本会依次尝试
`xsxk_operate / xsxk_xk / xsxk_xkBc / xsxk_saveXk / xsxk_doXk` 等候选路径，
**第一个被服务端接受的组合会被记住**，之后只走这一条，保证速度。

课表接口：`/kbcx/xskbcx_cxXsKb.html?gnmkdm=N2151&xnm=<学年>&xqm=<学期>`。

### 怎么判断"抢到了"

正方返回结果五花八门，`classify_submit` 按下面的优先级归类：

| 归类 | 触发条件 | 处理方式 |
| --- | --- | --- |
| **成功** `ok` | JSON `flag=1`，或含 `选课成功` | 移出目标，打印成功横幅 |
| **已是你的课** `already` | 含 `已选过` / `重复选课` / `已选定` | 视为成功，跳过 |
| **没抢到** `full` | 含 `已满` / `容量已满` / `余量不足` | **回查一次**，再继续轮询 |
| **未开放** `not_open` | 含 `不在选课时间内` / `未开放` | **继续投，不退避、不停止** |
| **真没戏** `stop` | 含 `无选课权限` 等 | 停止抢这门课，继续抢其它 |
| **掉线** `session` | 响应又是登录页 | 自动重新登录后继续 |
| **网关错误** `gateway` | 502/504 等 | 请求没到应用，立刻重投 |
| **端点不对** `unknown` | 404 / 返回 HTML | 换下一个候选端点 |

## 界面说明

| 按钮 | 作用 |
| --- | --- |
| ▶ 开始抢课 | 登录 → 进选课页 → 循环抢课，自动重试直到抢到 |
| ■ 停止 | 停止当前抢课 |
| **查看我的课表** | 拉取本学期课表，按星期分组显示 |
| **查看可选课程** | 读取可选课程并填进表格（**第一次用建议先点这个**） |
| 打开选课页 | 只跳到选课页面，方便你手动看 |
| 调试：导出表格 | 把页面表格的列/样本导出成 `table_debug.json` |

**课程表格支持双击**：双击某一行，会把它的课程名称自动填进「课程名称」输入框。
密码框里的内容**只保存在内存**，关闭程序即消失，不会写入任何文件。

另外也支持**浏览器登录**作为兜底（`python grab.py --browser --login-only`）：
弹出浏览器由你自己登录（扫码 / 手输密码都行），脚本完全不接触密码，
登录成功后把会话 Cookie 搬到 HTTP 客户端，之后全走高速 HTTP。
